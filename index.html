Telecom Customer 360Overview

I processed 48.5 million JSON viewing records and 2.37 million Parquet search records in PySpark, then built two Power BI pages on the resulting MySQL datasets.

The problem
The viewing logs identify subscriptions by contract, while the search logs identify people by user ID. I kept those two levels of detail separate so each dashboard could answer its own question.
What I did
  • Aggregated viewing time and active days by contract, then grouped contracts by viewing activity.
  • Ranked search terms per user and period with Spark SQL’s ROW_NUMBER, deduplicated keywords in Pandas, and classified them in batches with GPT-4o-mini.
  • Loaded the contract-level and user-level tables into MySQL via JDBC. The search table joins users present in both periods.
How data moves
  1. JSON and Parquet logs
  2. PySpark
  3. Contract and user datasets
  4. MySQL
  5. Power BI
The result
The viewing page covers about 1.92 million contracts. Among the 86,172 users with search logs in both periods (June 1–14 and July 1–14, 2022), 59,570 (69.13%) changed their top search category.

01Recruitment Data Platform

Kafka event ingestion and hourly recruitment metrics in MySQL.

May 2026Personal project

Download PDFPDF Source codeCode
Recruitment Data PlatformOverview
Next projectRetail Banking Lakehouse

I built a pipeline that ingests simulated recruitment events continuously, then runs a separate batch job every minute to aggregate six hourly KPIs.

The problem
Clicks, applications, and spend need a consistent reporting grain. The pipeline groups them by hour, job, publisher, campaign, and group.
What I did
  • Parsed simulated Kafka JSON events against an explicit schema in Spark Structured Streaming and wrote the event log to Cassandra with checkpointing.
  • Selected events from Cassandra using a MySQL timestamp high-water mark, joined job metadata to add company IDs, and wrote the aggregated KPIs to MySQL.
  • Scheduled the incremental PySpark job every minute in Apache Airflow and ran the stack with Docker Compose.
How data moves
  1. Kafka
  2. Spark streaming
  3. Cassandra
  4. Airflow and PySpark
  5. MySQL
The result
I checked the KPI formulas against 20 logged events from one job, publisher, campaign, and group in a single hour. The batch job appends its results, so an hour can have multiple output rows when its events span batches.

Retail Banking LakehouseOverview
Previous projectRecruitment Data Platform

I built a Customer 360 lakehouse with Spark, Iceberg, and MinIO and modeled a current mart for 10,000 simulated retail banking customers.

The problem
The project simulates a bank with customer data split across core banking, card, and CRM systems. Reporting needs a consistent customer snapshot, a record of changes, and restricted access to personal data.
What I did
  • Ingested simulated Oracle Core Banking and PostgreSQL card and CRM data via JDBC into Bronze, Silver, and Gold layers.
  • Modeled customer, account, product, and branch history with SCD Type 2. Checked key uniqueness and reconciled balances in Trino SQL.
  • Configured daily ETL in Apache Airflow, masked personally identifiable information (PII), and restricted marketing access to the sandbox using Trino roles.
How data moves
  1. Oracle and PostgreSQL
  2. Bronze
  3. Silver
  4. Gold
  5. Masked sandbox
  6. Trino and Superset
The result
In one manually triggered acceptance run, all eight child DAGs succeeded and 19 of 19 data quality checks passed. I built a Superset demo dashboard on the masked marts for RFM segmentation, churn risk, and cross-sell analysis.

Fashion E-commerceOverview

I built the Search & Recommendation Analytics dashboard in React and TypeScript and the React Native shopping app. The dashboard tracks search zero-result rate, recommendation click-through rate (CTR), and funnel conversion through payment.

The problem
Store staff need to see which searches return no products and where shoppers drop off after seeing a recommendation.
What I did
  • Aggregated search volume, trends, and queries with no results in MongoDB. The zero-result rate is the share of searches that returned no products in the selected period.
  • Tracked recommendation impressions, clicks, add-to-cart events, orders, and payments. Reported CTR, conversion at each step, and net attributed revenue.
  • Added period comparisons and filters for date, placement, and algorithm version across Home, Product Detail, and Cart. My teammate led the customer-facing web app.
How data moves
  1. Search and recommendation events
  2. MongoDB aggregations
  3. Search metrics and funnel
  4. Web admin dashboard
The result
Staff can review zero-result queries, compare recommendation placements, and see where the funnel drops off. In a separate offline benchmark on 100 Amazon Fashion cases, the Home recommender scored 0.0615 NDCG@5 versus 0.0063 for the Most Popular baseline.

01Hotel Digital Transformation

Booking reconciliation, occupancy analysis, and embedded Power BI.

Eight-week planClient project

Download PDFPDF Demo (sample data)Demo
Hotel Digital TransformationOverview
Next projectKalotoys WMS

I reconciled one branch’s booking and payment records in Excel, analyzed occupancy by month and bookings by channel, and configured the dashboard refresh for the booking system.

The problem
One branch of a three-branch hotel group in Ho Chi Minh City was missing its revenue target. Paper logs, Excel files, and payments needed to be reconciled before bookings could be compared by room type or channel.
The goal
Identify where occupancy and revenue fell short, then centralize bookings and payments to make future reporting and reconciliation easier.
The plan
  • Weeks 1–2: agree on KPI definitions, then digitize and standardize the records.
  • Weeks 3–4: confirm requirements, design and develop a trial system.
  • Weeks 5–8: pilot, train, adjust, evaluate and hand over.
What the data showed

I compared room nights, occupancy, room types, and booking channels with Excel PivotTables. The results cover one branch from June to October 2024.

  • Occupancy averaged 46.22% across the five months and fell to 17.83% in October.
  • Standard and Deluxe rooms made up 67.53% of nights sold and 66.84% of room revenue.
  • The staff booking channel accounted for 70.63% of bookings, even as occupancy remained low.
  • Collaborator bookings were priced only about 2.4% above OTA bookings.
The proposal
The analysis informed a proposal to raise offline and direct rates by 20% while keeping online travel agency (OTA) rates steady. The proposal drew on booking mix and rate comparisons.
Technology choices
  • Azure SQL Database stores operational records, and Azure App Service hosts the ASP.NET Core API.
  • Power BI provides the embedded reporting pages. Microsoft Fabric Warehouse stores the synchronized snapshots.
What I did
  • Built booking features and deployed the ASP.NET Core API to Azure App Service with Azure SQL Database.
  • Synced reporting snapshots from the Power BI REST API to Fabric Warehouse, ran DAX row-count checks, and configured Direct Lake refresh for the embedded report.
How data moves
  1. Front desk
  2. Next.js
  3. ASP.NET Core API
  4. Azure SQL
  5. Power BI reporting
  6. Fabric Warehouse
  7. Embedded report
Where it stands
The public front-desk demo uses sample data. The separate 20% revenue growth figure was a project target. Measuring it would require comparing actual revenue with a comparable period.

02Kalotoys Warehouse Management System

Stock movements, balance reconciliation, and Power BI inventory reporting.

Oct–Nov 2026, four-week planClient project

Download PDFPDF Live demoDemo
Kalotoys WMSOverview
Previous projectHotel Digital Transformation

I designed the movement ledger and stock balance model, then built Power BI dashboards to report inventory by material and location.

The problem
Kalotoys tracked material in Excel. Inconsistent records for withdrawals made it hard to see which shelf held the material or spot a shortage before production needed it.
The goal
Track receipts, issues, and balances by material and storage location so staff can reconcile counts and purchasing can identify stock below its threshold.
The plan
  • Week 1: survey the warehouse and standardize codes, units and specifications.
  • Weeks 2–3: design the database, build the app, then run a trial and guide users.
  • Week 4: acceptance and handover.
The data design
  • Designed an Excel ledger and data dictionary for eight movement types, with one row per material movement at a storage location.
  • Modeled the movement ledger and current balances separately in MongoDB Atlas.
  • Kept one balance per material and slot. Wrote each movement and its balance update in one database transaction.
  • Recorded transfers as paired outgoing and incoming rows to preserve total stock across locations.
Technology choices
  • MongoDB Atlas supports transactions across the ledger and balance collections.
  • Power BI shows receipts, issues, opening and closing stock, and low-stock alerts.
  • In the trial, I synced daily stock snapshots to Microsoft Fabric Warehouse for the reporting layer.
The solution
  • Forms for receipts, issues to the workshop, returns, transfers and adjustments, with the balance checked before issuing.
  • Stock lookup by slot, a rack map, low-stock alerts and export to Excel.
  • Transaction history and an opening, in, out and closing report for reconciliation.
How data moves
  1. Stock movement
  2. Next.js
  3. MongoDB Atlas
  4. Fabric Warehouse
  5. Power BI
What the reports reveal
In the sample snapshot for 10 November 2026, the report showed 28 occupied slots, six material codes below threshold, and seven locations over the 45-day stock-aging threshold.
Where it stands
Balances calculated from the ledger matched recorded stock in the reconciliation test across 660 simulated transactions and 713 ledger rows. The online trial uses sample data.
